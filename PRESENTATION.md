# CampusFlow API

## Слайд 1. CampusFlow API
**Сервис бронирования аудиторий на FastAPI и SQLite**
- `12` функциональных ручек (`+ /api/health`)
- `30 мин` шаг сетки (`09:00–18:00`)
- `167` автотестов (`97%` покрытия `app/`)

*Заметки спикера:* Бэкенд для бронирования аудиторий. Написан на FastAPI и чистом `sqlite3` без ORM, запускается одной командой и сам заливает начальные данные.

## Слайд 2. Расписание дня на примере A-101 (`RELATIVE:+1`)
Шкала рабочего дня `09:00–18:00`:
- `09:00–10:00` — свободно
- `10:00–11:30` — занято (`student1`, Консультация)
- `11:30–14:00` — свободно
- `14:00–15:30` — занято (`student2`, Семинар)
- `15:30–18:00` — свободно

Ключевые ограничения:
- Полуинтервалы `[start, end)`: стык `11:30` впритык не конфликтует.
- Отменённые брони (`cancelled`) игнорируются в слотах и конфликтах.
- Бронь на сегодня на время раньше `clock.now()` возвращает `400`.
- `free-slots` отдаёт максимальные непрерывные окна.

*Заметки спикера:* На примере комнаты A-101 видно, как работает сетка: отмены не занимают комнату, стыки разрешены, а прошедшие слоты сегодняшнего дня отклоняются.

## Слайд 3. Слои и схема SQLite
Слои `app/`:
- `routers/` — HTTP, заголовки, query
- `services/` — слоты и бронирования
- `repositories/` — чистый SQL
- `db.py` (`sqlite3`) — транзакции `BEGIN IMMEDIATE` без ORM

Таблицы БД (`app/db.py`):
- `users`: `id`, `login (UNIQUE)`, `display_name`, `role (student | admin)`
- `rooms`: `id`, `name (UNIQUE)`, `building (A–D)`, `floor >= 1`, `capacity > 0`, `equipment (JSON)`
- `bookings`: `id`, `room_id`, `user_id`, `date`, `start_time`, `end_time`, `status`, `comment`
- Индекс `idx_bookings_room_date_status (room_id, date, status)` и авто-seed (`3` юзера, `12` комнат, `7` броней с `RELATIVE:0/+1/+2`).

*Заметки спикера:* Чёткое разделение на транспорт, логику и SQL. Отказ от ORM дал прямой контроль над `BEGIN IMMEDIATE`, а модуль `clock.py` позволяет фиксировать время в тестах.

## Слайд 4. Карта API (11 из ТЗ + бонусная ручка)
| Метод и путь | Доступ | Назначение и коды |
|---|---|---|
| `POST /api/auth/login` | Публ. | Вход `password == login` → `200`, `400`, `401` |
| `GET /api/rooms` | Публ. | Фильтры `building`, `minCapacity`, `equipment` (И) → `200`, `400` |
| `GET /api/rooms/available` *(бонус)* | Публ. | Свободные комнаты на `date` и окно за 1 запрос → `200`, `400` |
| `GET /api/rooms/{id}` | Публ. | Карточка аудитории → `200`, `404` |
| `GET /api/rooms/{id}/free-slots` | Публ. | Свободные окна на `date` → `200`, `400`, `404` |
| `POST /api/bookings` | Токен | Создать бронь (`userId` из токена) → `201`, `400`, `404`, `409` |
| `GET /api/bookings/my` | Токен | Свои брони (`?status=active|cancelled`) → `200`, `400` |
| `DELETE /api/bookings/{id}` | Токен | Отмена своей брони → `200`, `403`, `404`, `409` |
| `GET /api/admin/bookings` | Admin | Все брони с фильтрами → `200`, `400`, `403` |
| `DELETE /api/admin/bookings/{id}` | Admin | Отмена любой брони → `200`, `403`, `404`, `409` |
| `POST / PUT /api/admin/rooms[/{id}]` | Admin | Создать / обновить аудиторию → `201/200`, `400`, `403`, `404` |

*Заметки спикера:* Кроме 11 обязательных ручек, добавлен `GET /api/rooms/available`, чтобы клиент не делал N+1 запрос при подборе комнаты.

## Слайд 5. Конвейер `POST /api/bookings` и гонка
Порядок проверок:
`401 Bearer` → `400 Поля / дата / время` → `404 Комната` → `BEGIN IMMEDIATE` → `409 / 201`

- **Гонка запросов:** проверка пересечений `start_a < end_b and start_b < end_a` и `INSERT` лежат в одной транзакции `BEGIN IMMEDIATE`. Параллельные запросы сериализуются на уровне SQLite.
- **Свободные окна (`slots.py`):** активные интервалы сортируются по старту, курсор за один проход от `09:00` до `18:00` собирает свободные промежутки без пустых слотов на стыках.

*Заметки спикера:* Транзакция `BEGIN IMMEDIATE` сразу берёт блокировку записи, поэтому два одновременных запроса на одно и то же окно не могут создать дублирующую бронь.

## Слайд 6. Единый JSON ошибок и тонкие места
```json
{
  "code": "BOOKING_CONFLICT",
  "message": "Аудитория уже забронирована на это время",
  "details": { "roomId": 1, "date": "2026-11-16", "startTime": "12:00", "endTime": "13:00" }
}
```
Коды: `VALIDATION_ERROR` (400), `UNAUTHORIZED` (401), `FORBIDDEN` (403), `ROOM_NOT_FOUND` (404), `BOOKING_NOT_FOUND` (404), `BOOKING_CONFLICT` (409), `ALREADY_CANCELLED` (409), `INTERNAL_ERROR` (500).

Что учтено в коде:
1. Токен проверяется до чтения тела — пустой `POST` без токена вернёт `401`, а не `400`.
2. В `roomId`, `floor`, `capacity` отсеиваются `bool` (`True/False`) через `is_strict_int`.
3. Админ на чужой брони в `DELETE /api/bookings/{id}` получает `403` — чужие снимаются через `/api/admin/bookings/{id}`.
4. `Utf8JSONResponse`: кириллица без `\uXXXX`, ошибки `422` и `500` завернуты в единый формат.

*Заметки спикера:* В FastAPI парсер тела обычно срабатывает до зависимостей. Мы читаем тело вручную внутри обработчиков, поэтому порядок `401 → 400 → 404 → 409` не нарушается.
